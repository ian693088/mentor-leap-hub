### 5\. How the backend works



This is one of the most important parts to understand.



Imagine someone fills out a volunteer registration form on the website. What happens after they click Submit?



Frontend



The registration page, form, buttons and navigation.



Backend / Application Logic



Validates the information, checks permissions and processes the request.



Database



Stores the registration and its review status.



Administrator Dashboard



An authorized administrator reviews the application and approves or rejects it.



Once approved, the volunteer can receive a notification, sign in, and access the relevant activities. The administrator should be able to see the updated status without manually editing the website code.

### 7\. Design the database before building all the pages



A well-organized database allows all the pages to work together.



Here is a practical starting structure.



| Database table | Information it stores                                   |

| -------------- | ------------------------------------------------------- |

| profiles       | User details and approved roles                         |

| programs       | Education, mentorship, STEM, sports and other programs  |

| projects       | Project descriptions, teams, milestones and progress    |

| memberships    | Membership applications and status                      |

| volunteers     | Volunteer interests, skills and availability            |

| opportunities  | Scholarships, internships, training and other listings  |

| applications   | Applications submitted by users                         |

| events         | Activities, dates, venues and registration              |

| news_posts     | Articles, announcements and updates                     |

| donations      | Verified contribution records and reconciliation status |

| impact_reports | Project results and performance indicators              |

| documents      | Approved reports, learning materials and resources      |



Each table would have a unique identifier, and related tables would link through IDs. For instance, a project belongs to a program, and a volunteer can be associated with several activities.



Do not create all these tables on the first day. Begin with profiles, programs, projects, and membership applications, then add more as you build the corresponding features.



### 8\. Build a proper login system with different user roles



Different people should not see the same dashboard or have the same permissions.



Super Administrator



Manages the overall platform, assigns authorized administrators, manages settings and oversees all departments.



Program Coordinator



Manages assigned programs, project updates, events and participant applications within their authorized area.



Member / Volunteer / Learner



Views relevant activities, updates their profile, registers for events and accesses permitted resources.



Public Visitor



Explores published information, views projects and submits permitted enquiries without necessarily creating an account.



A crucial point: hiding a button is not sufficient security. Supabase Row Level Security policies and server-side checks must control who can read or modify each record. Never expose a service-role key in your frontend.



Because the initiative may serve children, collect only the information you genuinely need, restrict access to sensitive records, and establish consent, safeguarding and data-retention procedures before enabling child accounts.

The dashboard could contain:

* Members: review membership applications, update approved records and assign appropriate roles.



* Programs: create new programs and appoint coordinators.



* Projects: add projects, set milestones, upload updates and track progress.



* Opportunities: publish listings and review applications.



* Events: schedule activities and manage registrations.



* Finance: record and reconcile contributions, expenses, budgets and funding allocations.



* Communications: publish announcements and send authorized notifications.



* Reports: produce activity summaries, participation statistics and impact reports.



* Settings: manage authorized accounts, access policies and platform configuration.



For financial transparency, record the source, date, amount, purpose and verification status of each contribution. Do not label a payment as received merely because someone filled out a donation form.



### 10\. How donations and financial support could work



A support page can start simply, with a donation enquiry form, partnership proposal form, and published funding priorities.



Later, you could integrate a payment provider that supports the payment methods you need in Kenya, including M-Pesa where available. The backend would verify payment confirmations through a trusted provider integration rather than trusting a message sent by the user's browser.



You could then have:



* A public page explaining the initiative's funding needs.



* A secure donation or contribution process.



* A private finance dashboard for authorized personnel.



* A ledger of verified contributions and approved expenditure.



* Public reports showing how funds were used, while protecting donor privacy.



If the initiative begins collecting public donations, establish appropriate financial controls, authorization procedures, and legal or organizational requirements before launching payment collection.



### 11\. How to build it, step by step



Here is the order I recommend. Building everything at once would make the project unnecessarily difficult.



### 1



Phase 1 — Define the organization



Write the mission, vision, objectives, target beneficiaries, programs, leadership structure and initial services. Decide what should be public and what should require login.

### 2



Phase 2 — Create the frontend



Build the shared header, footer, navigation, homepage and individual public pages. Establish consistent colors, typography, responsive layouts and reusable cards. At this stage, pages can use sample content.



### 3



Phase 3 — Set up Supabase



Create the database tables, user authentication, relationships, permissions and storage. Test that ordinary users cannot access private administrative data.



### 4



Phase 4 — Connect frontend to backend



Connect forms to the database, load projects dynamically, implement login and registration, and display appropriate messages when an operation succeeds or fails.



### 5



Phase 5 — Build the admin dashboard

### 6



Phase 6 — Test and launch



Test on Android phones and computers, validate forms, verify permissions, check loading speed, back up important data and deploy to Netlify. Start with a free subdomain, then connect a custom domain when ready.



### 7



Phase 7 — Expand gradually



Introduce verified donations, richer reports, notifications, mentorship matching, learner resources and additional features once the basic platform is stable and the necessary safeguards are in place.



### 12\. How the finished platform would operate



Imagine a school discovers THE BARAKA INITIATIVE online.



A teacher visits the Education page and finds a digital learning program. The teacher submits a partnership enquiry. The application appears in the admin dashboard, where an authorized coordinator reviews it.



After approval, the coordinator creates a learning event, publishes it on the website and accepts registrations. Volunteers can sign up, approved members can see their activities, and the team can later record how many learners participated.



Those figures contribute to an impact report. A potential partner can read that report, see the initiative's work and submit a funding proposal or partnership enquiry.



One connected system has now supported outreach, administration, program delivery, reporting and partnership development.



That is the type of workflow you should aim for.
